二、main.js 的组装顺序（为什么是这个顺序）

1. createScene()      // 先有舞台(地球)
2. createCampus()     // 再有演员(楼/路/树)
3. createPatrols()    // 然后让演员动起来(巡逻/波纹/雷达)
4. createAlarmManager()  // 业务大脑(告警闭环)
5. initUI()           // 舞台外围的仪表盘(面板/信息卡/图层开关)
6. 鼠标/按钮事件       // 最后把"遥控器"接线
7. 开场动画            // 幕布拉起

依赖关系决定顺序：UI 要显示告警数 → 告警管理器得先存在；告警要染红楼 → 楼得先画出来。以后你自己组装任何项目，先画依赖图（谁需要谁），按依赖从少到多排列。

四、高频答辩问答（预演）

Q1:为什么用 CesiumJS 而不用 Three.js/UE？

Cesium 生来面向"地理坐标 + 大范围场景"（自带地球、经纬度、地形、GIS 标准格式支持），数字孪生园区正好落在它 sweet spot；Three.js 是通用 3D 引擎，地理能力要全部自建；UE 效果强但部署重、需客户端，Web 大屏场景不合适。

Q2:模型怎么来的？为什么不是照片级？

建筑轮廓按真实卫星图数字化（位置/尺寸/朝向等比例还原），数据驱动生成——换校区只换数据表。照片级需要倾斜摄影或人工建模，成本高且本 demo 的重点是"孪生逻辑闭环"而非渲染精度；架构上预留了 3D Tiles/glTF 接入位。

Q3:数据是真的吗？怎么接真实数据？

前端模拟（随机游走+定时告警）。数据消费已收敛在明确接口处：面板读 stats、告警读 alarmManager——接真实系统时把数据源换成 WebSocket/MQTT 回调，业务与渲染代码零改动。

Q4:性能怎么样？

约 450 个实体 + 十几个图元，1080p 稳定 100+ FPS（现场可开 ?debug=1 展示帧率）。动画采用"静态几何+每帧仅更新矩阵/属性"，避免几何重建；若扩展到城市级，可切 Primitive 合批与 3D Tiles。

Q5:遇到过什么技术难点？（送分题，讲踩坑故事）

讲三个渲染停摆坑：CallbackProperty 动态实体、圆/多边形裸图元、逐帧相机旋转,在本机 Cesium 1.144+特定 GPU 会让画面全黑且无报错。我们做了特性开关二分排查页逐一定位,全部用"静态几何+矩阵/属性更新"方案绕行,并把结论沉淀成了内部避坑手册——体现的是工程排障能力。
